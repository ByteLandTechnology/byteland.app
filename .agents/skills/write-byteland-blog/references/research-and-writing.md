# Research, experiments and English writing

## Topic and evidence

Prefer a meaningful development from the previous 24–72 hours. Compare candidates
by date, reader value, source quality, testability and overlap with existing posts.
Record event date separately from announcement/publication date, exact version and
commit where applicable. If no fresh topic merits coverage, label an older technical
explainer honestly. Do not describe cumulative GitHub stars as recent growth.

Use multiple independent official or high-trust sources where available. Prefer
release notes, source commits, documentation, papers and maintainer statements.
Cross-check consequential claims and link directly to supporting pages. Avoid counting
copies of the same announcement as independent evidence. Explain contradictions.

Try the tool or repository in an isolated temporary workspace when feasible. Read
instructions, install hooks, test scripts and network behavior before executing them.
Do not allow test code to access production, credentials, unrelated personal data or
unapproved external destinations. Send only necessary sanitized code/results to an
authorized coding service. Never claim hands-on experience when execution was blocked.

Record environment, exact dependency versions, commands, fixtures, positive and
negative cases, expected versus actual results, and remaining coverage gaps. Separate
observed results, official claims and interpretation. A local mock does not establish
real DNS, cloud-network or production behavior.

If the article says readers can run a supplied experiment, include the actual harness,
lockfile or version pin, fixtures, license information, commands and results with a
working public link upon approval. Test those instructions from a clean checkout.
Do not publish a command pointing to a private or missing `experiment/` directory.

## Editorial relevance gate

Every section must directly help the reader understand the selected topic or make a
relevant decision. Do not add padding to satisfy an experiment or article-length
checklist. Run hands-on tests only when they answer a meaningful question about the
subject. A synthetic checker test is not evidence of the featured model's ability.
If access is unavailable, state the limitation briefly and use source-backed analysis.
Keep unrelated test records in review evidence, not the public article or video.
Remove a section when its result does not change the reader's understanding or action.

## STE and voice

Write in English using ASD-STE100 Issue 9 as the target. Keep prose natural, precise
and concrete; avoid promotional filler, generic opening/closing paragraphs and
invented personal anecdotes. Explain unfamiliar technical concepts with a small example.

Check approved words against their approved meaning and part of speech, grammar,
sentence limits for the applicable text type, noun clusters, pronouns and procedural
structure. Apply the standard's permitted technical-name and technical-verb conditions;
do not treat every unapproved word as automatically exempt. Keep a terminology list
with meaning, category and justification, and a review record naming the checks done.
Use an authorized copy of the standard/dictionary. Do not reproduce its protected text
in this repository. Automated sentence counts are a partial check, not a compliance
certificate. If full dictionary/grammar review is unavailable, disclose that limitation
and never claim full STE compliance.

Use the site's current metadata schema and existing tag spelling/capitalization.
Default article attribution is The ByteLand Team, subject to current repository history.
Verify commit identity through real history and authorized account; do not fabricate an author.
